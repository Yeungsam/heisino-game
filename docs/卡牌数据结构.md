# 卡牌与运行时物品数据结构

文档版本：0.4.0（2026-11-22，按实现提交 `67e27c0` 核对；卡库 `schema_version` 仍沿用兼容标识 `0.2.0`）

本文描述当前代码的数据契约。已部署与公网检查以[CloudBase 发布与验收](CloudBase发布与验收.md)记录为准；手机显示和多机交互仍按[全局回归测试用例](全局回归测试用例.md)独立验收。静态卡面、OCR、`DRAFT` 标记和实际战斗行为需要分别核对，不能互相替代。

## 1. 设计原则

- `cards.json` 只描述卡牌的静态定义，不保存某一局中的拥有者、耐久当前值或拾取状态。
- `item-instance.schema.json` 是早期通用实例结构，使用 `instance_id` 等 snake_case 字段；当前游戏引擎与接口使用 `instanceId`、`cardId`、`ownerId`、`nodeId`、`areaId` 等 camelCase 字段，不直接把该 Schema 当作线上响应格式。实际字段见[游戏引擎](../client/js/core/game-engine.js)、[账号搜索投影](../functions/heisino-account/service.js)和[独立搜索契约](搜索回合接口契约.md)。
- 客户端和服务端共用同一套字段；服务端负责校验、生成实例和推进状态。
- 当前 51 张卡牌使用 50 张卡面。蓝色「守卫圆盾」`ar_013` 复用「赌场圆盾」`ar_005` 的图片路径，按独立 ID 记录拾取、堆叠和仓库数量。
- 当前分类数量为 7 张武器卡、13 张防具卡、23 张物资卡和 8 张技能卡。
- 「四个六」`sk_002`、「额外骰子」`sk_003` 和「丢失银行卡」`loot_008` 已永久停用。退役 ID 必须追加至 [保留编号清单](../client/js/core/retired-cards.js)，不可重分配。构建和回归会拒绝复用。新版绿色物资「烟头」`loot_024` 价值 1,000 Gold，在休息室掉落。
- 旧账号与对局在下次成功访问时清除对应仓库数量和在局实例，已生成的房间不为此补货；资产流水保留原始 ID。
- OCR 原始结果保存在 `data/card-ocr.json`，人工校正后的权威数据保存在 `data/cards.json`。
- 原始 PNG 不进入小游戏主包；生成脚本会输出 768 像素长边 JPEG 到服务端资源目录。

## 2. 静态卡牌字段

| 字段 | 说明 |
|---|---|
| `card_id` | 稳定唯一 ID，不能因改名而变化 |
| `kind` | `EQUIPMENT`、`LOOT` 或 `SKILL` |
| `category` | 武器、防具、技能或物资 |
| `name` | 显示名称 |
| `description` | 从卡面识别并人工校正的玩法/数值说明 |
| `rarity` | 绿、蓝、紫、红或特殊 |
| `attack_multiplier` | 武器攻击倍率；非武器为 `null` |
| `defense_multiplier` | 防具防御倍率；非防具为 `null` |
| `economy` | 品级、售价、商店买价及价值来源 |
| `inventory` | 是否占用槽位、可否拾取/丢弃/掠夺 |
| `rules` | 装备要求、可用阶段和设计效果；有字段不代表效果已由运行时执行 |
| `assets` | 图标键、服务端卡面路径、原始文件名和 SHA-256 |
| `data_status` | `ACTIVE`、`DRAFT` 或 `BLOCKED` |
| `source.ocr_text` | 保留该卡原始 OCR 文本，方便复核 |

## 3. 价值规则

- [价格配置](../data/card-prices.json)按稳定 ID 记录品级与金币售价。武器、防具、物资取[飞书《房间物资表》](https://icnf9n2gye9f.feishu.cn/wiki/UKAjwhMWVivTG3kXiHIcEvKpnJd)，技能按品级 B 800 / A 5,000 / S 10,000 / SS 50,000。守卫圆盾只由守卫掉落，价值 1，商店不出售。价格品级和旧美术颜色独立。
- `economy.fixed_value` 是玩家卖给商店的单价，也用于仓库、背包、结算和战败没收排序。`purchase_price` 是玩家向商店购买的单价；A/B 级武器、防具、技能按售价的 120% 生成，其他为 `null`。
- 只改价格时执行 `node scripts/sync-card-economy.js`，同步主目录、卡牌云函数目录与客户端备用目录。完整美术构建也使用同一规则生成。
- 静态目录中防具的 `defense_multiplier` 仍为 `null`、状态为 `DRAFT`；当前互动战斗已由[战斗模块](../functions/heisino-account/combat-round.js)的 `DEFENSE_PERCENT` 按卡牌 ID 执行防御倍率（60%–100%）。有武器时使用其攻击倍率，无武器或无防具的一侧按 40% 计算。不能把目录中的 `DRAFT` 解读为“防具不生效”，也不能把目录描述当作全部附加效果已实现。
- 技能卡可以展示、带入和拖用，每小回合最多消耗一张；当前只消耗卡牌，不产生技能数值或附加效果。完整技能效果与静态目录状态的后续统一待定，不在本轮文档整理中变更数据。
- 武器、防具不再保存耐久属性，也不再因战斗次数销毁。原始 OCR 仅作为旧美术审计证据，不作为运行规则。
- 账号仓库按 `cardId → quantity` 保存，每种卡每格最多 99 张，超出在相邻格继续显示。战备最多带入 4 张，仅限武器、防具和技能；当前新版战备最多一件武器、一件防具。局内每张物品作为独立实例占一格，容量 10 格，同卡不堆叠；旧局超额物品保留并可翻页、丢弃，少于 10 件后才可继续拾取。同类装备拾取限制与战备一致。
- 账号归属、扣仓、返仓和失败损失由 `/api/account` 统一执行；详情见 [微信账号与资产闭环验收](微信账号与资产闭环验收.md)。
- 仓库总资产为金币加库存售价总和；局内资产为实际持有卡牌的售价总和（装备只算一次），变化量为当前价值减开局带入基准。成功撤离原物返仓，不自动兑换金币；商店售卡才增加金币。
- 商店通过 `POST /api/account/shop` 收购四类卡，常驻出售 16 种 A/B 级武器、防具和技能。多卡订单使用 `items: [{ cardId, quantity, unitPrice }]`，整单事务成交；库存或金币不足、旧报价等错误不产生部分成交。同一请求号与同一内容重试返回原回执，变更内容复用请求号被拒绝。账号在房间或未完成对局中不能交易。代码以[账号服务](../functions/heisino-account/service.js)为准。

## 4. 运行时拾取流程

房间物资、战斗掉落和玩家丢弃物品都使用物品实例：

```text
房间首次生成 → HIDDEN
  → 选择搜索区域，服务端每 0.5 秒揭示一件
可见物品（账号引擎 REVEALED；独立兼容搜索 EXPOSED）
  → 拖入背包，服务端确认可见、归属、容量及装备限制
IN_INVENTORY
  → 拖回搜索区域，服务端确认观察层与区域容量
DROPPED → 按该玩家的搜索权限重新拾取
```

背包满时，拾取请求被服务端拒绝，物品保持在原位置，不消失、不重复生成。

战后并非把败者全部物品开放给所有玩家：当前互动战斗按售价选取败者最高的两件，同价保留背包顺序；真人胜者在限定战利品窗口拾取。守卫获胜时没收两件；阵亡者剩余物品销毁，双倒不发战利品。具体分配、平局和轮空搜索由[战斗模块](../functions/heisino-account/combat-round.js)执行。

普通房间初始 0–4 件，概率依次为 20%、20%、30%、20%、10%；金库 6–10 件，概率依次为 40%、10%、10%、10%、30%；出生与撤离点为 0 件。数量与卡牌权重独立抽取，首次生成后不补货（包括抽到 0 件）。掉落池以[房型配置](../client/js/core/room-loot.js)为准。

## 5. 服务端接口

- `GET /health`：服务健康检查。
- `GET /api/cards`：返回全部卡牌及绝对卡面 URL。
- `GET /api/cards?category=skill`：按卡牌分类过滤。
- `GET /api/cards/:card_id`：返回单张卡牌。
- `GET /assets/cards/v2/:card_id.jpg`：返回长期缓存的新版卡面。改版使用新资源路径，旧地址保留给仍使用旧目录的客户端。

客户端通过 `client/js/api/cards.js` 拉取卡库，并在仓库、战备、搜索和背包界面按需加载卡面。接口失败时仅回退到内置结构化数据，卡面仍以服务端资源为准。

客户端配置必须分别维护 `cardApiBaseUrl` 与 `cardAssetBaseUrl`。服务端返回绝对 `card_art_url` 时优先使用该地址；使用内置目录降级时，必须用 `cardAssetBaseUrl + card_art_path` 解析卡面，禁止把卡面路径拼接到 API 网关域名。

生产环境使用两个同属 `cloud1-d5ghcmrajdca722b5` 的 HTTPS 域名：

- HTTP 网关：`https://cloud1-d5ghcmrajdca722b5-1510428576.ap-shanghai.app.tcloudbase.com/api/cards`
- 卡面静态托管：`https://cloud1-d5ghcmrajdca722b5-1510428576.tcloudbaseapp.com/assets/cards/`

客户端加载完整目录并通过本地投影展示分类；分类过滤、单卡详情及 `/health` 同时由服务端保留，供接口验证使用。生产单卡详情已在 2026-11-12 的发布记录中验证。

每次卡库或卡面更新后必须执行：

```bash
npm run test:regression -- --update-cases
npm run test:regression -- --rounds 5
npm run verify:cards:production
```

使用 Node.js 22 或更高版本。前两项在功能变更时更新实际用例索引并执行五轮发布回归，包含本地目录字段、稳定 ID、原图哈希、发布 JPEG、卡面复用和接口契约。云函数/共享数据变更还必须按[CloudBase 流程](CloudBase发布与验收.md)部署受影响函数；第三项验证生产目录字段和资源可访问性。最后在微信开发者工具和真机检查仓库、行动战备、装备背包及搜索揭示前后的画面。

## 6. OCR 与资源更新

```bash
swift scripts/ocr-cards.swift "/absolute/path/to/新版卡面导出目录" data/card-ocr.json
npm run cards:build -- "/absolute/path/to/新版卡面导出目录"
```

新版卡面来自 Figma 的 heisino 文件，导出后按 `scripts/build-card-catalog.js` 中的图层文件名映射到原卡牌 ID。卡背 `image 32.png` 生成到客户端搜索分包，供房间物品揭示前绘制。OCR 使用本机 Vision，识别文字仅供美术核对。改版使用新路径发布 JPEG 后更新云端卡库，并用线上验收脚本逐张与本地文件比对。真机检查搜索未揭示时的本地卡背、弱网下的远程卡面加载和仓库大图。

## 7. 后续扩展

增加新卡时先补充生成脚本清单，再重新运行 OCR 和目录生成；不应把局内拥有者、剩余耐久或拾取状态写入静态卡牌定义。
