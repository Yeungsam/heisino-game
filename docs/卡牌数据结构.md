# 卡牌与运行时物品数据结构

版本：0.2.0

## 1. 设计原则

- `cards.json` 只描述卡牌的静态定义，不保存某一局中的拥有者、耐久当前值或拾取状态。
- `item-instance.schema.json` 描述一张卡牌在某局中的实例状态。
- 客户端和服务端共用同一套字段；服务端负责校验、生成实例和推进状态。
- 当前卡库由 56 份卡牌美术经 OCR 与 SHA-256 去重后生成，共 52 张独立卡牌。
- 分类数量固定为：7 张武器卡、12 张防具卡、23 张物资卡、10 张技能卡。
- OCR 原始结果保存在 `data/card-ocr.json`，人工校正后的权威数据保存在 `data/cards.json`。
- 原始 PNG 不进入小游戏主包；生成脚本会输出 768 像素长边 JPEG 到服务端资源目录。

## 2. 静态卡牌字段

| 字段 | 说明 |
|---|---|
| `card_id` | 稳定唯一 ID，不能因改名而变化 |
| `kind` | `EQUIPMENT`、`LOOT` 或 `SKILL` |
| `category` | 武器、防具、技能或物资 |
| `name` | 显示名称 |
| `description` | 从卡面识别并人工校正的玩法/数值说明 |
| `rarity` | 绿、蓝、紫、红或特殊 |
| `attack_multiplier` | 武器攻击倍率；非武器为 `null` |
| `defense_multiplier` | 防具防御倍率；非防具为 `null` |
| `durability` | 最大耐久和每场战斗消耗；当前装备统一为 2/1 |
| `economy` | 购买价、固定物资价值及价值来源 |
| `inventory` | 是否占用槽位、可否拾取/丢弃/掠夺 |
| `rules` | 装备要求、可用阶段和技能效果 |
| `assets` | 图标键、服务端卡面路径、原始文件名和 SHA-256 |
| `data_status` | `ACTIVE`、`DRAFT` 或 `BLOCKED` |
| `source.ocr_text` | 保留该卡原始 OCR 文本，方便复核 |

## 3. 价值规则

- 装备价值来源为 `PURCHASE_PRICE`，正式结算时由购买价计算。
- 高价值物品使用 `FIXED_LOOT_VALUE`。
- 不在配置中重复保存一个可能与购买价不一致的“最终价值”。
- 武器和防具购买价未出现在卡面中，当前保留为 `null`，不得凭空推算。
- 防具倍率和技能的实际战斗执行尚未完成，因此相应卡牌标记为 `DRAFT`，但可正常展示和进入战备选择。

## 4. 运行时拾取流程

房间物资、战斗掉落和玩家丢弃物品都使用物品实例：

```text
HIDDEN
  → 第一次点击
REVEALED
  → 第二次点击且背包有空间
IN_INVENTORY
  → 拖拽到右下角丢弃
DROPPED
  → 其他玩家按同样规则拾取
IN_INVENTORY / EQUIPPED
  → 战败后生成可拾取掉落
DROPPED
```

背包满时，拾取请求被服务端拒绝，物品保持在原位置，不消失、不重复生成。

## 5. 服务端接口

- `GET /health`：服务健康检查。
- `GET /api/cards`：返回全部卡牌及绝对卡面 URL。
- `GET /api/cards?category=skill`：按卡牌分类过滤。
- `GET /api/cards/:card_id`：返回单张卡牌。
- `GET /assets/cards/:card_id.jpg`：返回长期缓存的真实卡面。

客户端通过 `client/js/api/cards.js` 拉取卡库，并在仓库、战备、搜索和背包界面按需加载卡面。接口失败时仅回退到内置结构化数据，卡面仍以服务端资源为准。

生产环境使用两个同属 `cloud1-d5ghcmrajdca722b5` 的 HTTPS 域名：

- HTTP 网关：`https://cloud1-d5ghcmrajdca722b5-1510428576.ap-shanghai.app.tcloudbase.com/api/cards`
- 卡面静态托管：`https://cloud1-d5ghcmrajdca722b5-1510428576.tcloudbaseapp.com/assets/cards/`

当前客户端只依赖完整目录和分类过滤接口；单卡接口及 `/health` 同时保留在本地 Node 服务中，用于开发和后续扩展。

## 6. OCR 与资源更新

```bash
swift scripts/ocr-cards.swift "/absolute/path/to/卡牌！" data/card-ocr.json
npm run cards:build -- "/absolute/path/to/卡牌！"
```

OCR 脚本使用本机 Vision 框架，不会把卡面上传给第三方识别服务。生成目录时必须人工复核低置信度文本，并保持已有 `card_id` 稳定。

## 7. 后续扩展

增加新卡时先补充生成脚本清单，再重新运行 OCR 和目录生成；不应把局内拥有者、剩余耐久或拾取状态写入静态卡牌定义。
