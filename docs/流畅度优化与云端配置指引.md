## 已确认的代码原因与改动

| 原因 | 本轮处理 |
| --- | --- |
| 原渲染循环每个 requestAnimationFrame 都完整重画页面 | 静态页面按需重绘；动画目标上限 30fps，状态变更不会因限帧丢失；后台不做绘制和游戏更新 |
| 原 currentState 每次绘制 JSON 深拷贝整份对局 | 绘制只读服务端投影的本地对象；同局同步不重复构建引擎索引 |
| 高 DPR 手机上整屏填充与阴影开销高 | 渲染 DPR 上限 2，逻辑坐标不变；离屏缓存基础页面、复用房间静态美术层 |
| 相同卡牌文案反复测量排版 | 有上限的文字换行缓存，避免随游玩时间无限增长 |
| 房间心跳每 800ms 请求一次，并把 accountBusy 设为 true | 心跳与前台操作锁分离；普通房间/地图通常 5 秒，搜索或临近阶段截止时 1 秒；正常操作响应刷新同步时间，避免刚操作完再发心跳 |
| 心跳慢请求及立即重试可能占住串行队列约 36 秒 | 心跳超时 4 秒、不立即重试；前台资产操作仍串行且重试沿用相同 requestId |
| 登录前串行等待远程卡库、进房等待搜索美术 | 使用随包校验卡库先登录，远程卡库后台更新；战备/匹配/对局中不热换卡库；搜索资源提前加载，进房先显示可用界面再替换美术 |
| 等待响应时缺少反馈、触控取消后可能留下拖拽状态 | 超过短暂等待显示轻量同步提示，重复操作明确提示；触控取消/切后台清理手势，不触发资产写入 |

点击反馈：游戏画布任意触点显示淡金色细圈和小光点，持续 500ms，扩散并淡出；不加音效、震动或额外图片，不遮挡交互。最多同时保留 8 个，抑制触控后合成的重复鼠标反馈。微信原生键盘、系统弹窗等平台覆盖层不由游戏 Canvas 绘制。

离屏 API 不支持、创建或复制失败时回退到普通绘制，不阻塞玩法。支持显式离屏 API 及小游戏在主画布创建后的 createCanvas 离屏路径；不会把主画布拿来当缓存。新增缓存只保留基础帧与房间美术帧，不缓存资产接口响应。小游戏画布语义可查阅[腾讯官方小游戏 API 类型定义](https://github.com/wechat-miniprogram/minigame-api-typings)。

上述效果只是“收到触控”的反馈，不代表服务端已确认拾取、移动或结算。未曝光物资不提前展示，金币和仓库仍由服务端事务决定。

## 当前验证结果

- `npm run check` 语法检查通过；共 122 项测试，118 项通过，4 项端口 HTTP 测试在当前沙箱出现 `listen EPERM 127.0.0.1`，不能称为通过；系统审批服务故障阻止了允许端口后的复测。单独运行账号客户端/API、性能 UI 和计时头内存处理器等 22 项验证全部通过。
- 性能专项验证覆盖：500ms 到期清除、透明度/扩散、反馈数量上限、合成鼠标去重、静态页不重复绘制、动效复用缓存、无离屏回退、DPR、卡库慢请求不阻塞登录、同步期间仍接受操作、旧响应不覆盖新状态、房间静态层缓存、绘制不调用深拷贝。
- 新增不监听端口的 HTTP 处理器内存链路测试，验证登录、昵称保存、扣仓、失败结算和 Server-Timing 计时头；它不替代真实网络与云数据库验证。
- `npm run benchmark:render` 是合成微基准，不是手机帧率：模拟 10 秒、60Hz 调用时，旧循环应重画 600 次，新静态页调度只需 1 次。600 次状态快照开销一次本机测得约 47.63ms；优化后渲染不再执行这些深拷贝。此数字不包含 GPU、美术、网络或真机负载，不能称为实际 FPS 提升幅度。

## 区分客户端、网络与服务端

客户端账号模块在内存保留最近 60 次公共性能样本；排队加请求耗时达到 800ms 时输出一行 `[account-perf]`。它只含 action、queueMs、requestMs、serverMs、status，不写本地持久化、不发送额外埋点、不记录身份、请求体、登录 code 或凭证。

| 字段/现象 | 排查方向 |
| --- | --- |
| queueMs 大 | 客户端串行队列正在等待已有请求；后台心跳已限时且不再占交互锁 |
| requestMs 大、serverMs 小 | 排查手机网络、HTTP 网关、函数初始化等 handler 外等待；不能仅据差值断言是网络 |
| serverMs 大 | handler 内身份交换、昵称审核、数据库事务或计算；对局操作应重点检查数据库与函数运行时间 |
| 首次请求显著慢、紧接着的请求快 | 结合函数初始化/冷启动日志验证，不能只凭一次请求确定冷启动 |
| 不等接口时，滑动、动画仍卡 | 优先检查客户端帧耗时、纹理和机型，不应先升级服务器 |

`serverMs` 来自本轮新增的 `Server-Timing: app;dur=...` 响应头，是 handler 内的业务处理时间，不包含完整冷启动、网关和手机网络。**当前尚未部署此头，线上样本 serverMs 为 null 属正常。** 不把健康检查的 200 或耗时当作数据库对局性能证明。

需要发送诊断时，仅截真机调试 Console 中 `[account-perf]` 行；不要发送 Network 的 Authorization 请求头或 Storage 登录凭证。

## 需要时如何优化 CloudBase 配置

当前仓库声明账号函数为 Nodejs20.19、256MB、20 秒超时、上海环境；这些是源码配置，不是本轮重新读取控制台的结果。尚无新证据证明内存或并发配额不足，因此本轮没有升级、购买或开预置并发。

### 先看监控，不先改套餐

1. 登录 CloudBase，选择环境 `cloud1-d5ghcmrajdca722b5`。
2. 进入“计算/云函数”，选择 `heisino-account`，查看监控/日志中的调用运行时间、初始化/冷启动、内存使用、错误和限流。正式账号对局使用这个函数，不能只看旧 `heisino-game` 搜索测试函数。
3. 比较首次打开和连续操作各数次的结果，记录同一时段的平均值、P95（若控制台提供）和慢请求。监控入口及基础参数见[CloudBase 基础配置](https://docs.cloudbase.net/cloud-function/function-configuration/config)。

### 如果已确认主要是冷启动

进入该函数“预置管理 → 新增预置并发”，在控制台支持的函数版本上先评估 1 个实例。确认业务 HTTP 路由实际命中被预置的版本/别名；只给未使用版本预置不会改善实际请求。具体入口和版本快照语义见[官方预置并发说明](https://docs.cloudbase.net/cloud-function/alias)。

预置并发会保留常驻实例，可能产生持续费用。先查看计费与预算再确认，不要无依据给全部三个函数都开预置，也不要通过定时空调用保活规避配置和计费。

### 如果连续操作也慢

- handler 耗时高：先查数据库请求/事务延迟及函数计算和内存指标。账号读写以文档 ID 定位，不能靠随意新增索引解决所有问题；保留账号及流水的事务和版本校验。
- 内存接近上限或计算受限：在“函数配置”评估从 256MB 调到 512MB 做小流量对比，记录耗时与费用，再决定是否保留；不是保证有效的修复。
- 并发限流：根据实测 QPS 和请求耗时评估实例/并发上限，不要盲目拉满配置。不同实例之间仍依靠数据库事务处理竞争。
- handler 快但端到端慢：比较 Wi-Fi/移动网络，核对函数和数据库地域；不要为了测试直接迁移现有资产数据库。
- 不要把超时从 20 秒改到更大当作提速；不要关闭 HTTPS/合法域名校验；不要对登录、账号、心跳、对局 POST 开 CDN 共享缓存。

### 本轮服务端代码如何上线

本轮服务端仅增加业务耗时响应头，没有变更结算规则。在系统操作权限恢复后，可在项目根目录终端运行 `npm run account:deploy`，脚本沿用已有环境变量，不需要把密钥发给任何人。部署之后再验证业务响应的 Server-Timing 和真机日志。本轮尚未执行该部署；客户端优化不依赖这个头，头不存在仍可正常游戏。
