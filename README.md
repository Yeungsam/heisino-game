# 大劫卡西诺（Heisino Game）

一款横版 2.5D 多人搜打撤卡牌游戏。

玩家从离岸码头出发，进入卡西诺中央赌场，在有限回合和不断增加的风险中搜索物资、与其他玩家战斗、掠夺战利品，并尝试从唯一撤离点安全返回。

## 项目状态

当前阶段：MVP 本地规则原型（里程碑 M1）。

已完成：

- 核心玩法、世界观和视觉方向定义。
- 3 人联机、12 回合、5×5 逻辑地图等 MVP 基线确认。
- 首批 7 张武器卡和 3 张高价值物品卡配置。
- 卡牌静态定义和运行时物品实例数据结构。
- GitHub SSH 远程仓库配置。
- 可在微信开发者工具中运行的横屏 Canvas 规则原型。
- 移动、搜索、拾取、丢弃、基础自动战斗、三人分流和警报圈规则引擎。
- 首批核心规则自动化测试。

当前暂不包含：

- 完整联机服务端。

- PvE 和敌人 AI。
- 正式音效和背景音乐。
- 完整生产级美术资源。

## MVP 规则基线

### 对局与回合

- 每局 3 名玩家。
- 匹配最长等待 5 分钟；超时后房间自动解散。
- 匹配期间玩家可以主动取消；房间为空时销毁。
- 每局最多 12 个全局回合。
- 每回合总时长 55 秒。
- 玩家每回合只能移动到相邻节点，也可以停留原节点。
- 玩家同时提交移动；倒计时结束或所有玩家提交后统一结算。
- 玩家未操作时，默认停留原节点。
- 选择移动期间不显示节点人数；移动结算后统一展示移动轨迹。

### 节点与遭遇

- 地图使用 5×5 逻辑节点结构。
- 三名玩家从三个复活点出生，第四个角点为唯一撤离点。
- 多名玩家进入同一节点时自动触发遭遇处理。
- 两人同节点时直接进入战斗。
- 三人同节点时随机选择两人战斗，另一人进入搜索状态。
- 单人进入节点时，通过点击房间物品进行搜索。
- 同节点三人时，节点物资随机分为两部分：一部分进入战斗轮，一部分进入搜索轮。
- MVP 暂不实现 PvE。

### 战斗

每场战斗最多 3 个小回合，每个小回合依次执行：

```text
技能预判 5 秒
→ 掷 3 颗 D6 并分配 10 秒
→ 攻防结算与动画 2 秒
→ 耐久清理
```

- 玩家 HP：30。
- 3 颗 D6 可自由分配至攻击区和防御区。
- 战斗中 HP 归零时立即战败。
- 3 轮结束后，累计造成伤害较高者获胜。
- 累计伤害相同时，剩余生命值百分比更高者获胜。
- 装备最大耐久：2。
- 每完成一场战斗，攻防装备耐久减少 1。
- 战斗中不受到警报圈伤害。

### 警报圈

- 第 10 回合开始进入警报圈。
- 第 10—12 回合每个回合开始时立即扣除 10 HP。
- HP 归零或低于 0 时立即战败。

### 搜索、拾取与背包

- 房间物品第一次点击时显示。
- 第二次点击时尝试拾取。
- 搜索受当前回合倒计时限制。
- 背包满时无法拾取，物品保持在原位置。
- 房间内未拾取物品持续保留。
- 玩家丢弃的物品持续保留。
- 玩家可以将背包物品拖拽到页面右下角丢弃。
- 装备占用背包槽位。
- 战败掉落物和房间物品使用同一套待拾取机制。

## 技术方向

### 客户端

目标平台为微信小游戏。M1 使用微信小游戏原生 Canvas + CommonJS JavaScript 快速验证规则闭环，不引入第三方运行时。完成规则验证后，再根据美术动效复杂度决定继续原生实现，或迁移至 Cocos Creator + TypeScript。核心规则引擎保持与渲染层解耦，便于后续迁移。

### 服务端

建议采用腾讯云 CloudBase：

- CloudBase 数据库：玩家、卡牌、库存、对局和结算数据。
- CloudBase 云托管：Node.js/TypeScript 权威房间服务。
- WebSocket：房间状态、倒计时、移动结算和战斗结果推送。
- 云函数：账号初始化、配置读取、管理工具和非实时业务。

核心原则：随机数、移动结算、战斗结果、掉落、掠夺和最终结算全部由服务端决定。

## 本地运行

1. 打开微信开发者工具，选择“小游戏”。
2. 导入仓库内的 `client/` 目录；AppID 已配置为测试应用。
3. 选择横屏模拟器并编译。
4. 点击高亮的相邻节点移动；搜索阶段对物资点击两次完成显示和拾取。
5. 可将背包物品拖到右下角丢弃区。

运行自动化测试：

```bash
npm test
```

## 开发顺序

1. M1：本地规则原型与单元测试（当前）。
2. M2：补齐撤离、结算、手动骰子分配和规则边界。
3. M3：CloudBase 权威房间、3 人匹配、同步和断线恢复。
4. M4：接入正式 UI、角色、场景、卡面与动效。
5. M5：封闭测试、性能优化、合规检查和微信小游戏发布。

声音暂不进入首版内容验收，但客户端会保留音效事件接口和全局静音状态，便于后续由音效组接入。

## 贡献与协作约定

- PMO/产品经理负责范围、优先级和最终规则确认。
- 游戏策划负责玩法、卡牌、地图、掉落和数值定义。
- 美术组负责角色、场景、卡牌、UI 和动效资源。
- 音效组负责后续音效与音乐资产。
- 开发实现负责客户端、服务端、配置系统、自动化测试和发布技术支持。
- 规则冲突必须先记录并确认，再进入代码实现。
