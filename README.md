# 大劫卡西诺（Heisino Game）

横版 2.5D 多人搜打撤卡牌微信小游戏。玩家从赌场外围进入 5×5 区域搜索物资、处理玩家遭遇，并从唯一撤离点安全离场。

## 测试包临时规则

- “开始匹配”会在本机依次模拟两名玩家加入，用来验证完整流程，不代表正式线上匹配。
- “单人测试·立即开始”会直接补齐两个机器人，仅在开发测试包保留。

- 毒圈在回合开始时结算，HP 归零立即战败。玩家活到撤离点所在回合结束即成功撤离。

## 已冻结规则基线

- 移动选择最多 15 秒，进入房间后独立启动 50 秒搜索轮。回合持续推进至撤离、战败、放弃或断线结算。
- 每回合可停留或移动到上下左右相邻节点；所有人选择完成后统一结算。
- 选择阶段隐藏其他玩家人数与目的地，结算后显示移动轨迹。
- 第 1–5 回合中央金库锁定，第 6 回合开放。
- 两人同节点进入战斗；三人同节点随机两人战斗、一人搜索，房间物资随机分半。 多人中独自移动到普通房间或开放的金库时，有 30% 概率遇到守卫，战斗规则与单人一致。
- 普通/出生房间初始化 4 件物资，中央金库 10 件，撤离点不生成固定物资；每 2 秒曝光一件并保留，拖入 10 格背包完成拾取；满格仍可补足同卡未满 99 的堆叠。
- 从第 12 回合开始，每回合开始时存活玩家扣 5 HP。回合提示显示剩余生命，警报圈开启或造成伤害时一并提示。
- 撤离点为 `(4,4)`。结束该大回合的搜索、战斗和战利品阶段后，存活且位于撤离点的玩家自动撤离。

## 技术结构

```text
client/
  assets/                    # 已授权的本地视觉参考资源
  data/                      # 客户端卡牌投影
  js/core/                   # 与画面解耦的规则、战斗、匹配模型
  js/main.js                 # 微信小游戏 Canvas 场景和交互

data/
  cards.json                 # 51 张卡牌的静态配置
  card-ocr.json              # 原始 OCR 结果与坐标审计记录
  cards.schema.json          # 卡牌配置 Schema
  item-instance.schema.json  # 运行时物品实例 Schema

docs/
  M1规则原型说明.md
  M2完整流程测试包说明.md
  M2.1战备页面验收说明.md
  游戏产品流程图.md
  卡牌数据结构.md

tests/                       # Node.js 自动化测试
scripts/                     # OCR、卡牌目录和资源生成脚本
server/                      # 卡牌 API 与服务端卡面资源
Dockerfile                   # CloudBase 云托管构建入口
functions/heisino-cards/     # 生产环境卡牌 Web 云函数
functions/heisino-game/      # 权威搜索回合 Web 云函数与 CloudBase 事务存储
functions/heisino-account/   # 微信身份、账号资产与当前机器人对局的统一权威服务
cloudbaserc.json             # CloudBase 环境与函数配置
```

客户端采用微信小游戏原生 Canvas + CommonJS JavaScript。卡牌目录通过 `GET /api/cards` 获取，账号与当前对局通过 `/api/account` 接口执行，卡面通过静态资源地址按需加载；卡牌目录失败可使用内置目录，账号资产不允许本地写入降级。

## 本地运行

1. 运行 `npm run account:build` 构建可独立部署的账号云函数；完成账号服务配置后，运行 `npm run server` 可启动本地卡牌、搜索与内存账号联调服务（内存账号重启即清空）。
2. 如需调试本地服务，将 `client/js/config.js` 中的卡牌和对局 API 地址临时设置为开发机局域网地址和端口 `3000`；默认配置连接正式 CloudBase API。
3. 打开微信开发者工具，选择“小游戏”，导入仓库中的 `client/` 目录。
4. 使用横屏模拟器编译；完成微信登录与首次资料填写，检查仓库仅有礼包三张卡。默认客户端连接 CloudBase，因此新账号服务未部署配置前会显示登录重试页。
5. 从开始页进入行动战备，选择最多 4 张卡牌后点击“开始匹配”。
6. 可等待本地模拟匹配，或点击“单人测试·立即开始”。

自动化检查：

```bash
npm run check
```

使用 Node.js 22 执行 `npm run test:regression -- --rounds 5` 可运行五轮全局回归。功能变更时同步更新[全局回归测试用例](docs/全局回归测试用例.md)并重新生成[自动化用例索引](docs/自动化用例索引.md)。

生产卡牌服务联调检查：

```bash
npm run verify:cards:production
```

生产搜索服务全链路联调检查：

```bash
npm run verify:search:production
```

重新导入美术并生成卡牌目录：

```bash
npm run cards:build -- "/absolute/path/to/卡牌！"
```

## 前后端联动开发基线

从 M2.2 起，任何涉及玩家资产、卡牌、匹配、房间、战斗、搜索、背包或结算的迭代，都必须同时评估客户端表现、服务端接口、权威数据、静态资源和异常降级，不能把“页面能画出来”视为功能完成。

固定开发流为：先冻结数据契约与错误状态，再实现服务端/配置，再接入客户端，随后完成本地联调、生产环境联调、自动化测试和真机画面验收。测试至少同时覆盖：接口状态与响应结构、数据数量/唯一性/字段约束、客户端字段投影、静态资源可访问性、失败降级，以及最终页面是否展示正确数据。

API 域名和静态资源域名必须独立配置。开发工具的“不校验合法域名”只能用于排查，不得作为体验版或发布版的验收条件。详细原则见 [游戏项目管理与设计框架](游戏项目管理与设计框架.md) 和 [卡牌数据结构](docs/卡牌数据结构.md)。
